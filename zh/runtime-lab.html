Runtime Lab

并行、并发、组合

ALUX 支持可重放的长交易：独立任务可以同时推进，交易则通过消息协作。预订场景演示的是目标模型——让相关的跨系统状态变化作为一个原子结果结算。

定位去中心化并发运行时
执行运行、交互、等待、结算
边界能力约束下的工作流

先分清三件事

三个词很像，
但它们解决的问题不同

并行让互不依赖的交易同时执行。并发让交易通过通道交互：一笔交易可以等待另一笔交易发来匹配消息，再继续执行。组合把不同执行系统中的状态转移放进同一个结算边界，使它们作为一次可审计的原子状态转移完成结算。

在当前 ALUX 运行时中，独立任务可以并行推进，交易通过消息协作，执行也能跨区块恢复。独立系统之间的原子组合仍属于架构目标。

并行

航班、酒店、接送和保险
同时查询

它是什么意思
并行指多项互不依赖的工作同时执行。旅行智能体可以同时查询航班、房间、接送和保险，不必让一项查询排在另一项后面。
ALUX 如何做到
并行执行是 ALUX 进程演算的原生能力：交易不共享内存，任何交互都只能通过元组空间通道发生。互不依赖的交易因此可以在不同 TVM 执行轨道上推进，提交时若出现状态重叠，再由 Block Merge 裁决。
它能做什么
同样时间里能完成更多独立工作，但单靠并行，既不能让这些工作交换消息，也不能让一笔长交易等待后继续。

并行可以同时得到多项结果，但不会让这些任务彼此交互。

并发

预订等待房态，
收到回复后继续

它是什么意思
并发从工作之间发生交互开始。预订可以在通道中留下等待条件，酒店服务稍后发回匹配的房态消息，预订再继续。
ALUX 如何做到
等待方的接收请求（consume）会作为等待资源保存在元组空间中；另一笔交易发出（produce）匹配数据后触发 COMM 事件，生成等待方的后续执行（continuation），并让执行上下文从非活动状态恢复为运行状态。当存在多个候选匹配时，ReplayTrie 记录实际选中的 COMM，供验证者确定性重放。
它能做什么
旅行智能体可以让一笔长交易跨区块等待房态、API 回复或用户决定，并在条件满足后继续执行，同时不阻塞无关工作。

并发把一次回复变成下一步执行：消息匹配会生成新的后续执行，而不是让停住的轨道原地重启。

组合

房间锁定与付款
共同确认

它是什么意思
组合不是把多项工作简单打包。这个示例的目标，是让房间锁定与付款授权要么共同提交，要么都不提交。
ALUX 如何做到
当前运行时已经提供元组空间协作、限定范围的 OCAP 引用、跨区块后续执行、ReplayTrie 与 Block Merge。基于这些原语，在彼此独立的外部系统之间实现端到端原子组合，仍属于设计目标。
它能做什么
预期结果是避免出现只扣款却没有房间，或只锁房却没有完成付款的半成品预订。

目标组合模型让不同系统得到一个全有或全无的结果；并发负责传递共同提交前的消息。

运行路径

是什么让一项服务持续运行

长时间运行的服务之所以保持一致，是因为每一步都能执行、交互、携带显式权限、进行确定性重放，并沿一条可验证的原子路径完成结算。

运行

TVM 进程生命周期

进程可以分叉，在一个区块中等待，并在后续区块恢复，而不必重新启动本地执行上下文。

交互

元组空间 + COMM

等待中的取用（Consume）与另一笔交易的写入（Produce）相匹配；匹配会唤醒后续执行，而无关工作继续推进。

授权

OCAP 权限边界

不可伪造的能力引用被显式传递，让每一步只获得所需权限；身份不会自动把无关权限带入当前环境。

重放

ReplayTrie

只记录真正影响结果的非确定性 COMM 选择，使验证者能够复现同一段执行。

结算

BlockGit + Block Merge

并发工作进入经过验证的 Fringe；相互重叠的结果会在最终确认前被判定为接受、拒绝或待定。

Runtime Lab 展示当前的并行执行与消息驱动并发，并说明目标中的原子组合模型。GLVM 则描述更广泛的架构：如何将这套逻辑模型扩展到区块链节点、云服务和个人设备。

为什么重要

不是更快的区块，而是持续运行的服务

并行负责推进彼此独立的任务，并发负责消息驱动的交互以及等待与恢复。ALUX 当前已实现这些运行时基础，并正在面向跨系统原子组合继续建设。

只有并行

吞吐更高，但没有交易依赖与消息匹配。

只有并发

交易可以交互和等待，但跨系统结果仍可能分别结算。

只有组合

存在原子边界，但没有交互与等待，就承载不了持续运行的依赖关系。
