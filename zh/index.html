服务可暂停、可恢复

TVM 字节码进程通过类型化元组空间通道通信。服务可以等待外部输入、稍后恢复，并保留自己的执行上下文。

智能体、预约、审批和工作流可以成为持续服务，而不只是一次性交易。

对象能力安全模型

原生支持 OCAP

  • 命名空间
  • 委托
  • 权限收窄
  • 生命周期类型

权限有清晰边界

OCAP 将权限表示为不可伪造的通道引用。进程只能使用自己创建或被显式传入的引用；能力还可继续衰减，并受通道使用类型与生命周期规则约束。

每个任务只获得完成它所需的能力；与任务无关的权限不会进入当前执行环境。

ALUX 能实现哪些普通智能合约做不到的事？
ALUX 将智能合约模型扩展为面向长时间任务的去中心化持久执行引擎。工作流可以运行并发进程、跨区块挂起、等待外部工具或人工响应、恢复执行并汇合结果，同时不暴露半完成状态。由运行时介导的外部通道可与受支持的链下服务交互，无需单独编排预言机与中继器。该架构旨在把同一种原子模型横向扩展，使跨分片影响一同提交或一同中止；跨分片执行仍在路线图中。
为什么 ALUX 天然适合 AI 智能体？
链上智能体天然是一笔长交易。调用 LLM 或工具需要时间，等待人工响应同样需要时间；这类工作流无法被压缩成瞬时完成的单区块调用。ALUX 使其能够保留执行上下文、挂起，并在输入到达后恢复，协调并发智能体，再通过可重放执行完成最终确定。
ALUX 只是又一条更快的 L1 吗？
不是。更快的 L1 加速的是同一种抽象：发生在单个区块内的一次性状态更新。ALUX 是面向长交易（Long Transaction）的去中心化并发运行时；交易可以等待、恢复、汇合多个通道，或选择第一个就绪的通道，其状态更新不再受区块边界限制。通过 GLVM 架构——虚拟机抽象——同一笔逻辑交易被设计为能够越过区块边界，并进一步延伸到分片与系统边界。
其他一些区块链也声称支持跨区块交易，ALUX 有何不同？
关键词是原子性。

补偿 / Saga： commit → commit → ✗ fail → run compensating undo
每一步都在本地提交，中间状态可见，补偿本身也可能失败，而且外部影响并非总能撤销。这属于最终一致性。包括 ICP 与 Rialo 在内的一些异步区块链采用了这一模型。它更容易实现，却不适合需要更强 ACID 保证的应用。

ALUX 全有或全无： stage → stage → ✗ fail → discard everything
只有整笔交易提交时，任何内容才会提交。发生中止时，未提交的影响会被全部丢弃，不会暴露任何局部状态。这才是跨区块高度的真正 ACID 原子性。
ALUX 如何保证长交易的确定性？
ReplayTrie 记录会影响执行结果的非确定性 COMM 选择，使验证者能够在 ALUX 运行时边界内逐比特精确地重放同一执行结果。
什么是对象能力（OCAP）？
对象能力（OCAP）是一种安全模型：一段代码只有在被明确授予某项资源的引用（即能力）后，才能访问该资源。在 OCAP 系统中，同一个对象引用既标识资源（designation），也授予使用该资源的权限（authorization）。
为什么 OCAP 是一种更强且可组合的安全模型？
对象能力（OCAP）之所以是一种更强的安全模型，是因为权限由显式且不可伪造的能力来表示，而不是依赖全局身份或访问控制列表。它遵循“指称即授权”（designation is authorization）原则：持有某项能力既标识相应资源，也授予使用该资源的权限，从而消除环境权限（ambient authority）并缩小攻击面。由于能力可以被安全地委托、衰减和撤销，安全策略会局部化到相关对象，而不是散落在中心化权限系统中。这使 OCAP 天然具备可组合性：复杂应用、智能合约和 AI Agent 工作流可以由各自安全的组件构建，同时仍然遵循最小权限原则。
ALUX 原生支持 OCAP 意味着什么？
ALUX 的元组空间虚拟机（TVM）在字节码层直接实现对象能力（OCAP）模型。其指令集不包含任何可伪造或任意构造对象引用的操作，因此能力只能通过显式委托获得。这保证了所有权限既不可伪造，也只能被明确转移。
现有智能合约开发者能直接用吗？
TVM 在隔离沙箱中运行 EVM 字节码，因此大多数 EVM 合约只需少量修改即可迁移到 ALUX。ALUX 还通过一组常用的 eth_* JSON-RPC 方法提供兼容以太坊的视图。
