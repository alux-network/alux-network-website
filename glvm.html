GLVM

Global Logical Virtual Machine

One logical execution layer, coordinated across many machines.

GLVM is the developer-facing execution abstraction ALUX is building from its concurrent runtime. A TVM provides the concrete engine on each participating machine; the GLVM model brings execution state, processes, replay, replication, and consensus into one logical layer.

The core definition

One TVM per machine, coordinated through one logical execution model

TVM is the bytecode execution engine on one machine. GLVM defines the system-level execution abstraction across participating TVMs. It is not another bytecode VM; developers target one logical model while deterministic replay, execution continuity, replication, finalization, and consensus are coordinated beneath the abstraction.

Composite execution extends the model so multiple concurrent transactions can share a higher-level settlement boundary; cross-block continuity provides the vertical foundation for that direction.

    At the finalization boundary, eligible state is committed; rejected tentative state is discarded.

Atomicity model

Tentative intermediate state does not become confirmed state until finalization; a failed path is discarded instead of repaired later through compensating transactions.

Native off-chain read

An authenticated HTTPS GET can suspend, record the response, replay, and resume. The data source still determines truth, and irreversible off-chain side effects remain outside rollback.

Object-capability security

Give the task one key—not the user’s badge

In the CEO–Bob example, identity-based access can carry the ambient authority represented by the CEO’s badge into the task. With object capabilities, the task receives only one key that names Bob’s record. The TVM enforces the reachable boundary at runtime. Without a capability reference to another pre-existing object, the task cannot name or reach it.

Broad identity authority

The badge carries unrelated access into the task

Even when the task concerns Bob alone, the identity authority represented by the CEO’s badge can still cover Financials and the records of Alice, Carol, and Bob.

Explicit object capability

The task receives one key that names Bob’s record

This key represents an unforgeable name that identifies Bob’s record. Without a capability reference to another pre-existing object, the task cannot name or reach it. The TVM checks that boundary at runtime.

POLA · Principle of least authority

Model safeguards can reduce unsafe behavior, but capability boundaries enforce least authority at runtime. If an agent has only the key that names Bob’s record, compromise stays within that object instead of expanding to all the identity authority represented by the CEO’s badge.

Terminology

Here, “key” visually represents an OCAP unforgeable name—a capability reference. It is not a cryptographic key. This guarantee applies to TVM-native, capability-mediated interactions; hosted EVM permissions and external services need their own controls.

Runtime anatomy

Nine capability areas behind the GLVM abstraction

GLVM is not a second bytecode VM. These nine architecture views—from TVM execution, object capabilities, and replay to BlockGit, guest VMs, and developer tooling—show the capability system behind its logical execution model.

  1. 01
    Bytecode VMCore runtime

    TVM · tuple space · COMM

    The concrete concurrent engine runs bytecode and lets independent processes exchange data and continuations through channels.

  2. 02
    SecurityCore runtime

    Native object capabilities

    Unforgeable references make reachable authority explicit and let the runtime enforce least-authority boundaries.

  3. 03
    AtomicityCore runtime

    Cross-block atomic execution

    Execution contexts can suspend across blocks, resume from preserved continuations, and reach a deferred finalization boundary.

  4. 04
    FinalityCore runtime

    BlockGit · fringe · merge

    A block DAG, deterministic leader rotation, and merge rules converge concurrent chain-side work without a permanent leader.

  5. 05
    ReplayCore runtime

    ReplayTrie · trace

    Recorded non-deterministic choices and execution traces let validators reproduce the accepted path.

  6. 06
    NetworkCore runtime

    Peer and validator network

    The node layer carries proposals, blocks, state evidence, and validator coordination beneath the execution abstraction.

  7. 07
    LanguageCore runtime

    Tolang → tolangc → .tox

    Tolang describes concurrent processes; the compiler lowers source into TVM-executable bytecode.

  8. 08
    Guest VMsEVM core · WASM roadmap

    EVM host · WASM roadmap

    The EVM runs as a stateful guest through TSAC-style coordination. WASM extends the heterogeneous-VM direction.

  9. 09
    ToolingDeveloper surface

    Compiler · LSP · playground

    The compiler, LSP, playground, test suite, and diagnostics bring the execution model into developer workflows.
