Runtime Lab

병렬성 / 동시성 / 조합 가능성

ALUX는 재실행 가능한 장기 트랜잭션을 지원합니다. 독립 작업은 함께 실행되고 트랜잭션은 메시지로 조율됩니다. 예약 시나리오는 서로 연관된 시스템 간 결과를 하나의 원자적 결과로 정산하는 목표 모델을 보여 줍니다.

포지셔닝탈중앙화 동시성 런타임
실행실행, 상호작용, 대기, 정산
경계권한 범위 안의 워크플로

세 가지를 먼저 구분하기

비슷해 보이지만 해결하는 문제가 다릅니다

병렬성은 서로 독립적인 트랜잭션을 동시에 실행합니다. 동시성은 트랜잭션이 채널을 통해 상호작용하게 합니다. 한 트랜잭션은 다른 트랜잭션의 일치하는 메시지를 기다렸다가 실행을 이어갈 수 있습니다. 조합은 서로 다른 실행 시스템의 상태 전환을 하나의 감사 가능한 원자적 상태 전환으로 묶습니다.

현재 ALUX 런타임에서는 독립 작업을 병렬로 실행하고, 트랜잭션을 메시지로 조율하며, 블록을 넘어 실행을 재개할 수 있습니다. 서로 독립된 시스템을 아우르는 원자적 조합은 아직 아키텍처 목표입니다.

병렬

항공편, 호텔, 이동 수단, 보험을
동시에 조회합니다

무엇을 뜻하나
병렬 실행은 서로 의존하지 않는 작업을 동시에 처리하는 것입니다. 여행 에이전트는 한 조회가 끝나기를 기다리지 않고 항공편, 객실, 이동 수단, 보험을 함께 찾을 수 있습니다.
ALUX는 어떻게 하나
병렬 실행은 ALUX 프로세스 대수의 기본 특성입니다. 트랜잭션은 메모리를 공유하지 않고 모든 상호작용은 튜플 공간 채널로 제한됩니다. 따라서 독립 트랜잭션은 서로 다른 TVM 실행 레인에서 진행되며, 커밋 시 상태가 겹치면 Block Merge가 판정합니다.
무엇을 가능하게 하나
같은 시간 안에 더 많은 독립 작업을 끝낼 수 있습니다. 하지만 병렬 실행만으로는 작업끼리 메시지를 주고받거나, 장기 트랜잭션이 기다렸다가 계속 실행되게 할 수 없습니다.

병렬은 여러 답을 동시에 찾게 하지만, 그 작업들을 서로 상호작용하게 만들지는 않습니다.

동시성

예약은 객실 상태를 기다리고
답변이 오면 계속됩니다

무엇을 뜻하나
동시성은 작업 사이에 상호작용이 생길 때 시작됩니다. 예약은 채널에 대기 조건을 남기고, 호텔 서비스는 나중에 일치하는 객실 상태 메시지를 보내 그 조건을 충족할 수 있습니다.
ALUX는 어떻게 하나
기다리는 consume은 튜플 공간에 자원으로 저장됩니다. 다른 트랜잭션의 produce가 이를 일치시키면 COMM 이벤트가 발생해 continuation을 실행하고 Execution Context를 Inactive에서 Running으로 되돌립니다. 가능한 일치가 여러 개일 때 ReplayTrie가 선택된 COMM을 기록해 결정적으로 재현합니다.
무엇을 가능하게 하나
여행 에이전트는 하나의 장기 트랜잭션을 블록을 넘어 유지할 수 있습니다. 객실 상태, API 응답, 사용자 결정을 기다렸다가 관련 없는 작업을 막지 않고 계속 실행합니다.

동시성은 답변을 다음 실행으로 바꿉니다. 메시지 일치는 멈춘 레인을 제자리에서 다시 움직이는 것이 아니라 새로운 후속 실행을 만듭니다.

조합

객실 확보와 결제가
함께 확정됩니다

무엇을 뜻하나
조합은 단순히 여러 작업을 묶는 것이 아닙니다. 이 예에서는 예약 시스템이 객실을 확보하고 결제 시스템이 승인을 완료합니다. 두 상태 변화는 함께 적용되거나 둘 다 적용되지 않습니다.
ALUX는 어떻게 하나
현재 런타임은 튜플 공간 조율, 범위가 제한된 OCAP 참조, 블록 간 후속 실행, ReplayTrie, Block Merge를 제공합니다. 서로 독립된 외부 시스템을 끝까지 원자적으로 조합하는 기능은 이 기본 요소를 바탕으로 한 설계 목표입니다.
무엇을 가능하게 하나
목표는 결제만 되고 객실은 확보되지 않거나, 객실만 확보되고 결제가 끝나지 않는 반쪽짜리 예약을 피하는 것입니다.

목표 조합 모델은 서로 다른 시스템에 전부 성공하거나 전부 취소되는 하나의 결과를 제공하고, 동시성은 공동 커밋에 이르기까지의 메시지 교환을 담당합니다.

전체 런타임 체험

하나의 원자적 예약 모델링하기

네 단계로 목표 조합 모델을 살펴보세요. 예약과 결제 확인을 함께 시작하고, 객실 상태 대기를 남긴 뒤, 호텔의 일치하는 메시지를 전달하고, 마지막으로 공동 확정을 모델링합니다.

01두 확인 시작

예약과 결제 확인이 각각 진행됩니다.

02객실 상태 기다리기

예약이 채널에 객실 상태 조건을 남깁니다.

03호텔 응답

일치하는 메시지가 예약의 후속 실행을 깨웁니다.

04함께 확정

객실 확보와 결제 승인이 하나의 결과로 커밋됩니다.

순서대로 실행

1단계부터 시작합니다. 예약과 결제는 같은 런타임에서 관리되지만 상태는 서로 독립적입니다.

병렬두 확인이 함께 실행

독립 작업이 하나의 전역 대기열 뒤에 줄 서지 않습니다.

동시성예약이 호텔 응답을 기다림

의존 관계는 채널에 남고 런타임 전체를 막지 않습니다.

메시지 일치응답이 다음 단계를 생성

COMM이 후속 실행을 만들며, 일치가 비결정적일 때만 ReplayTrie가 선택을 기록합니다.

조합객실과 결제가 함께 확정

목표는 재현 가능한 정산 증거와 함께 전부 성공하거나 전부 취소되는 하나의 결과를 만드는 것입니다.

런타임 경로

서비스를 계속 살아 있게 하는 것

장기 실행 서비스가 일관성을 유지하는 이유는 각 단계가 실행되고, 상호작용하고, 명시적 권한을 전달하고, 결정적으로 재생되며, 검증 가능한 하나의 원자적 경로를 따라 정산될 수 있기 때문입니다.

실행

TVM 프로세스 수명 주기

프로세스는 분기하고 한 블록에서 기다린 뒤 다음 블록에서 이어지며, 로컬 실행 컨텍스트를 다시 시작하지 않습니다.

상호작용

튜플 공간 + COMM

대기 중인 consume이 다른 트랜잭션의 produce와 만나면 후속 실행이 깨어나고, 무관한 작업은 계속 진행됩니다.

권한 부여

OCAP 권한 경계

위조할 수 없는 권한 참조를 명시적으로 전달해 각 단계에는 필요한 권한만 줍니다. 신원은 무관한 권한을 자동으로 범위 안에 끌어오지 않습니다.

재현

ReplayTrie

결과에 영향을 주는 비결정적 COMM 선택만 기록해 검증자가 동일한 실행을 재현할 수 있게 합니다.

정산

BlockGit + Block Merge

동시 작업은 검증된 프린지로 들어가며, 중복 결과는 최종성 전에 승인, 거부, 미결정으로 분류됩니다.

다음 계층

여러 실행 환경을 잇는 하나의 논리 런타임

Runtime Lab은 현재의 병렬 실행과 메시지 기반 실행을 보여 준 뒤, 목표로 하는 원자적 조합 모델을 설명합니다. GLVM은 이 논리 모델을 블록체인 노드, 클라우드 서비스, 개인 기기로 확장하는 더 넓은 아키텍처를 다룹니다.

왜 중요한가

더 빠른 블록이 아니라 지속 실행되는 서비스

병렬성은 독립 실행을, 동시성은 메시지 기반 상호작용과 대기·재개를 담당합니다. ALUX는 현재 이 런타임 기반을 구현했으며, 시스템 경계를 넘는 원자적 조합을 향해 개발 중입니다.

병렬만 있다면

처리량은 늘지만 트랜잭션 의존성과 메시지 일치는 없습니다.

동시성만 있다면

트랜잭션은 상호작용하고 기다릴 수 있지만 시스템 간 결과는 따로 정산될 수 있습니다.

조합만 있다면

원자적 경계는 있지만 상호작용과 대기가 없으면 장기 의존성을 담을 수 없습니다.
