권한은 범위 안에 머뭅니다

OCAP은 권한을 위조할 수 없는 채널 참조로 표현합니다. 프로세스는 자신이 생성했거나 명시적으로 전달받은 참조만 사용할 수 있고, 그 권한은 축소되거나 채널 사용 유형 및 수명 주기 규칙의 제약을 받을 수 있습니다.

각 작업에는 필요한 권한만 주어지며, 작업과 무관한 권한은 실행 컨텍스트에 들어오지 않습니다.

여러 샤드에 걸친 하나의 트랜잭션 — 로드맵

목표 모델은 참여하는 모든 샤드의 업데이트를 하나의 트랜잭션 경계 안에 스테이징합니다. 어느 샤드의 로컬 호출이든 실패하면 스테이징된 업데이트는 관측 가능해지기 전에 모두 폐기됩니다. 크로스 샤드 실행은 현재 런타임에 구현되어 있지 않습니다.

애플리케이션이 부분 커밋된 상태를 Saga 보상으로 복구하지 않아도 수평으로 확장할 수 있습니다.

가상 머신 추상화ALUX Runtime

GLVM은 TVM의 동시 실행, 네이티브 OCAP 지원, 블록 간 원자성, BlockGit 최종성을 하나의 논리 실행 계층으로 통합합니다.

하나의 논리 실행 계층

TVM 실행, 네이티브 OCAP 지원, 크로스 블록 커밋 로직, BlockGit 최종성이 하나의 런타임 추상화 안에서 만납니다.

이 아키텍처는 체인, 프라이빗 클라우드, 향후 클라이언트 기기 실행 환경 전반에서 하나의 개발자 모델을 유지합니다.

ALUX에서는 일반 스마트 컨트랙트가 못 하던 무엇이 가능해지나요?
ALUX는 스마트 계약 모델을 장기 실행 작업을 위한 탈중앙화 내구 실행 엔진으로 확장합니다. 워크플로는 동시성 프로세스를 실행하고, 블록을 넘어 중단하며, 외부 도구나 사람을 기다렸다가 재개하고 결과를 join하면서도 절반만 완료된 상태를 노출하지 않습니다. 런타임이 중개하는 외부 채널은 별도의 오라클·릴레이어 조합 없이 지원되는 오프체인 서비스와 상호작용할 수 있습니다. 아키텍처는 같은 원자적 모델을 수평으로 확장해 크로스 샤드 효과가 함께 커밋되거나 중단되도록 설계되어 있으며, 크로스 샤드 실행은 로드맵에 남아 있습니다.
왜 ALUX는 AI 에이전트에 적합한가요?
온체인 에이전트는 본질적으로 장기 트랜잭션입니다. LLM이나 도구를 호출하는 데는 시간이 걸리고, 사람의 응답을 기다리는 데도 시간이 필요합니다. 이 워크플로를 즉시 끝나는 단일 블록 호출에 억지로 맞출 수는 없습니다. ALUX에서는 실행 컨텍스트를 보존하고, 중단한 뒤 입력이 도착하면 재개하며, 여러 에이전트를 동시에 조정하고, 재현 가능한 실행으로 확정할 수 있습니다.
ALUX는 또 하나의 더 빠른 L1인가요?
아닙니다. 더 빠른 L1은 같은 추상화, 즉 한 블록 안에서 일어나는 일회성 상태 업데이트를 가속합니다. ALUX는 기다리고, 재개하고, 여러 채널을 합치거나, 가장 먼저 준비된 채널을 선택할 수 있는 장기 트랜잭션(Long Transaction)을 위한 탈중앙화 동시성 런타임입니다. 상태 업데이트는 더 이상 블록 경계에 제약되지 않습니다. GLVM 아키텍처인 가상 머신 추상화를 통해 동일한 논리 트랜잭션은 블록 경계를 넘어 샤드와 시스템 경계까지 확장되도록 설계됩니다.
다른 체인도 크로스 블록 트랜잭션을 지원한다고 주장합니다. ALUX는 무엇이 다릅니까?
핵심은 원자성입니다.

보상 / Saga: commit → commit → ✗ fail → run compensating undo
각 단계는 로컬에서 커밋되고 중간 상태가 노출되며, 보상 자체도 실패할 수 있고 외부 효과를 항상 되돌릴 수 있는 것은 아닙니다. 이것은 최종 일관성입니다. ICP와 Rialo를 포함한 일부 비동기 체인은 이 모델에 의존합니다. 구현은 더 쉽지만 더 강한 ACID 보장이 필요한 애플리케이션에는 적합하지 않습니다.

ALUX 전부 아니면 전무: stage → stage → ✗ fail → discard everything
전체 트랜잭션이 커밋될 때까지 아무것도 커밋되지 않습니다. 중단되면 커밋되지 않은 효과는 모두 폐기되고 부분 상태는 관찰되지 않습니다. 이것이 블록 높이를 아우르는 진정한 ACID 원자성입니다.
ALUX는 장기 트랜잭션의 결정성을 어떻게 유지하나요?
ReplayTrie는 실행 결과에 영향을 주는 비결정적 COMM 선택을 기록합니다. 따라서 검증자는 ALUX 런타임 경계 안에서 동일한 실행 결과를 비트 단위로 정확하게 결정론적으로 재실행할 수 있습니다.
객체 권한(Object Capability, OCAP)이란 무엇입니까?
객체 권한(Object Capability, OCAP)은 코드가 어떤 리소스에 접근하려면 그 리소스에 대한 참조, 즉 권한(capability)을 명시적으로 전달받아야만 하는 보안 모델입니다. OCAP 시스템에서는 동일한 객체 참조가 리소스를 지정(designation)하는 동시에 그 리소스를 사용할 권한을 부여(authorization)합니다.
OCAP가 더 강력하고 조합 가능한 보안 모델인 이유는 무엇입니까?
객체 권한(OCAP)이 더 강력한 보안 모델인 이유는 권한을 전역 ID나 접근 제어 목록이 아니라 명시적이고 위조할 수 없는 capability로 표현하기 때문입니다. OCAP은 ‘지정이 곧 권한 부여다(designation is authorization)’라는 원칙을 따릅니다. capability를 보유하면 리소스를 식별하는 동시에 해당 리소스의 사용 권한을 얻으므로, 주변 권한(ambient authority)을 제거하고 공격 표면을 줄일 수 있습니다. capability는 안전하게 위임·축소·회수할 수 있어 보안 정책이 중앙 집중식 권한 시스템 전반에 흩어지지 않고 관련 객체에 국소화됩니다. 따라서 OCAP은 자연스럽게 조합 가능하며, 최소 권한 원칙을 유지하면서 독립적으로 안전한 구성 요소로 복잡한 애플리케이션, 스마트 컨트랙트, AI 에이전트 워크플로를 구축할 수 있습니다.
ALUX가 OCAP를 네이티브로 지원한다는 것은 무엇을 의미합니까?
ALUX의 튜플 공간 가상 머신(TVM)은 객체 권한(OCAP) 모델을 바이트코드 수준에서 직접 구현합니다. 명령어 집합에는 임의의 객체 참조를 위조하거나 생성하는 연산이 없으므로, 권한은 명시적 위임을 통해서만 획득할 수 있습니다. 따라서 모든 권한이 위조 불가능하고 명시적으로 이전된다는 점이 보장됩니다.
기존 스마트 컨트랙트 개발자도 사용할 수 있나요?
TVM은 격리된 샌드박스에서 EVM 바이트코드를 실행하므로 대부분의 EVM 계약을 최소한의 변경으로 ALUX에 마이그레이션할 수 있습니다. ALUX는 일반적으로 사용되는 eth_* JSON-RPC 메서드 집합을 통해 Ethereum 호환 뷰도 제공합니다.
