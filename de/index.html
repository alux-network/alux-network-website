Die globale VM entsteht

Stellen Sie sich eine logische virtuelle Maschine vor, die überall läuft – auf öffentlichen Blockchains, in privaten Clustern und in Client-Umgebungen wie Smartphones und Browsern – und dabei den zugrunde liegenden Zustand, Threads, die Replikation und den Konsens abstrahiert. Entwickler schreiben ein nebenläufiges Programm; der Ausführungsort wird zur Konfigurationsentscheidung statt zu einer architektonischen Einschränkung. Seine Bestandteile werden weiterhin gemeinsam als ein atomares Ergebnis übernommen. Das ist die Abstraktion virtueller Maschinen, und ALUX entwickelt sie.

Dienste pausieren und werden fortgesetzt

Bytecode-Prozesse der TVM kommunizieren über typisierte Tuple-Space-Kanäle. Sie können auf Eingaben warten, später fortgesetzt werden und ihren Ausführungskontext beibehalten.

Agenten, Reservierungen, Genehmigungen und Abläufe können als laufende Dienste statt als einmalige Transaktionen ausgeführt werden.

Sicherheit durch Objekt-Capabilities

Native OCAP-Unterstützung

  • Namensräume
  • Delegation
  • Einschränkung
  • Lebenszyklustypen

Begrenzte Berechtigungen

OCAP stellt Berechtigungen durch fälschungssichere Kanalreferenzen dar. Ein Prozess kann nur Referenzen verwenden, die er selbst erstellt hat oder die ihm ausdrücklich übergeben wurden. Capabilities lassen sich anschließend durch Kanalnutzung und Lebenszyklusregeln einschränken.

Jede Aufgabe erhält nur die erforderlichen Capabilities; sachfremde Berechtigungen gelangen nie in ihren Ausführungskontext.

Eine Transaktion über viele Blockhöhen hinweg

Segmente und Partitionen bewahren den Fortschritt an Haltepunkten. ReplayTrie, Isolation und Commit-Regeln ermöglichen Validatoren, dieselbe Transaktion über spätere Blöcke hinweg fortzusetzen und zu reproduzieren.

Warten Sie auf Genehmigungen, externe Daten oder einen anderen Dienst, ohne eine Folge teilweise übernommener ALUX-Zustände offenzulegen.

Eine Transaktion über viele Shards hinweg – Roadmap

Das Zielmodell hält Aktualisierungen auf allen beteiligten Shards hinter einer Transaktionsgrenze zurück. Scheitert ein shardlokaler Aufruf, werden alle vorgemerkten Aktualisierungen verworfen, bevor sie sichtbar werden. Cross-Shard-Ausführung ist in der aktuellen Runtime nicht implementiert.

Horizontal skalieren, ohne Anwendungen zu zwingen, teilweise übernommene Zustände durch Saga-Kompensation zu reparieren.

GLVM führt nebenläufige TVM-Ausführung, native OCAP-Unterstützung, blockübergreifende Atomarität und BlockGit-Finalität in einer logischen Ausführungsschicht zusammen.

Eine logische Ausführungsschicht

TVM-Ausführung, native OCAP-Unterstützung, blockübergreifende Commit-Logik und BlockGit-Finalität treffen in einer Runtime-Abstraktion zusammen.

Die Architektur bietet ein einheitliches Entwicklermodell für Chain, private Cloud und künftige Ausführungsumgebungen auf Client-Geräten.

Lang laufende KI-Agenten auf der Chain

Ein Ablauf startet mehrere Agenten parallel. Einige rufen die Claude-API auf, während andere Schritte auf Eingaben des Nutzers warten. Der Haupt-Agent setzt erst fort, wenn jeder Zweig abgeschlossen ist – auch wenn der Ablauf etwa 30 Minuten dauert. Claude und Nutzereingaben werden auf Anwendungsebene eingebunden; ALUX stellt dauerhafte Fork-, Wait-, Join-, Capability-Weitergabe- und wiederholbare Ausführungsfunktionen bereit.

03

Atomare Cross-Shard-Ausführung

Vertrag a auf Shard A merkt eine Zahlung für ein Ticket vor, das von Vertrag b auf Shard B verwaltet wird. Scheitert b, weil das Ticket bereits verkauft wurde, wird die Zahlung von a zurückgerollt. Erst wenn beide Schritte erfolgreich sind, werden Zahlung und Ticketbesitz gemeinsam übernommen; andere Transaktionen sehen keinen Teilzustand. Atomare Cross-Shard-Ausführung ist ein Roadmap-Ziel und heute keine verfügbare Funktion.

Häufig gestellte Fragen

FAQ

Klicken Sie auf eine Frage, um die Antwort zu sehen

Was wird mit ALUX möglich, was gewöhnliche Smart Contracts nicht können?
ALUX erweitert das Smart-Contract-Modell zu einer dezentralen Engine für dauerhafte Ausführung lang laufender Aufgaben. Ein Ablauf kann nebenläufige Prozesse ausführen, blockübergreifend angehalten werden, auf externe Tools oder Menschen warten, fortgesetzt werden und Ergebnisse zusammenführen, ohne einen halbfertigen Zustand offenzulegen. Über die Runtime vermittelte externe Kanäle können mit unterstützten Off-Chain-Diensten interagieren, ohne separate Oracle- und Relayer-Abläufe. Die Architektur soll dasselbe atomare Modell horizontal erweitern, sodass Cross-Shard-Effekte gemeinsam übernommen oder abgebrochen werden; Cross-Shard-Ausführung steht weiterhin auf der Roadmap.
Warum wurde ALUX für KI-Agenten entwickelt?
Ein On-Chain-Agent ist von Natur aus eine Langtransaktion. Ein Aufruf eines LLM oder Tools dauert; auch das Warten auf eine menschliche Antwort braucht Zeit. Der Ablauf lässt sich nicht in einen sofortigen Aufruf innerhalb eines Blocks zwingen. ALUX bewahrt den Ausführungskontext, hält den Ablauf an, setzt ihn bei eingehenden Eingaben fort, koordiniert nebenläufige Agenten und finalisiert über wiederholbare Ausführung.
Ist ALUX nur eine weitere, schnellere L1?
Nein. Schnellere L1s beschleunigen dieselbe Abstraktion: einmalige Zustandsaktualisierungen innerhalb eines Blocks. ALUX ist eine dezentrale nebenläufige Runtime für Langtransaktionen, die warten, fortgesetzt werden, Ergebnisse über mehrere Kanäle zusammenführen oder den zuerst verfügbaren Kanal auswählen können; ihre Zustandsaktualisierungen sind nicht mehr an eine Blockgrenze gebunden. Mit seiner GLVM-Architektur – Abstraktion virtueller Maschinen – ist ALUX darauf ausgelegt, dieselbe logische Transaktion über Blockgrenzen hinaus auf Shard- und Systemgrenzen auszuweiten.
Einige andere Chains behaupten ebenfalls, Cross-Block-Transaktionen zu unterstützen. Was unterscheidet ALUX?
Entscheidend ist die Atomarität.

Kompensation / Saga: commit → commit → ✗ fail → run compensating undo
Jeder Schritt wird lokal übernommen, Zwischenzustände sind sichtbar, Kompensationen können ebenfalls scheitern und externe Effekte lassen sich nicht immer rückgängig machen. Das ist letztliche Konsistenz. Einige asynchrone Chains, darunter ICP und Rialo, setzen stark auf dieses Modell. Es ist einfacher umzusetzen, aber ungeeignet für Anwendungen, die stärkere ACID-Garantien benötigen.

ALUX: Alles oder nichts: stage → stage → ✗ fail → discard everything
Nichts wird übernommen, bevor die gesamte Transaktion erfolgreich abgeschlossen ist. Bei einem Abbruch werden nicht übernommene Effekte verworfen und kein Teilzustand wird sichtbar. Das ist echte ACID-Atomarität über Blockhöhen hinweg.
Wie hält ALUX Langtransaktionen deterministisch?
ReplayTrie zeichnet nichtdeterministische COMM-Entscheidungen auf, die sich auf die Ausführung auswirken. So ermöglicht es eine bitgenaue deterministische Wiederholung innerhalb der ALUX-Runtime, damit Validatoren dasselbe Ausführungsergebnis reproduzieren können.
Was sind Object Capabilities (OCAP)?
Object Capability (OCAP) ist ein Sicherheitsmodell, in dem ein Stück Code nur dann auf eine Ressource zugreifen kann, wenn ihm ausdrücklich eine Referenz (eine Capability) auf diese Ressource übergeben wurde. In einem OCAP-System identifiziert dieselbe Objektreferenz eine Ressource (Bezeichnung) und erteilt zugleich die Berechtigung, sie zu verwenden (Autorisierung).
Warum ist OCAP ein stärkeres und kombinierbares Sicherheitsmodell?
Object Capability (OCAP) ist ein stärkeres Sicherheitsmodell, weil Berechtigungen durch explizite, fälschungssichere Capabilities statt durch globale Identitäten oder Zugriffskontrolllisten dargestellt werden. Es folgt dem Prinzip, dass Bezeichnung zugleich Berechtigung ist: Wer eine Capability besitzt, bezeichnet damit eine Ressource und erhält die Erlaubnis, sie zu verwenden. So entfallen implizite Umgebungsberechtigungen und die Angriffsfläche wird kleiner. Da Capabilities sicher delegiert, eingeschränkt und widerrufen werden können, gelten Sicherheitsrichtlinien lokal für die beteiligten Objekte, statt über ein zentrales Berechtigungssystem verstreut zu sein. Dadurch lässt sich OCAP auf natürliche Weise kombinieren: Komplexe Anwendungen, Smart Contracts und KI-Agenten-Abläufe können aus unabhängig abgesicherten Komponenten aufgebaut werden, während das Prinzip der geringsten Berechtigung erhalten bleibt.
Was bedeutet native OCAP-Unterstützung in ALUX?
Die tupelraumbasierte virtuelle Maschine (TVM) von ALUX implementiert das Object-Capability-Modell (OCAP) direkt auf Bytecode-Ebene. Der Befehlssatz enthält keine Operationen zum Fälschen oder Erzeugen beliebiger Objektreferenzen. Dadurch können Capabilities nur durch explizite Delegation erworben werden. So wird sichergestellt, dass alle Berechtigungen fälschungssicher und ausdrücklich übertragen sind.
Können Entwickler bestehender Smart Contracts ALUX nutzen?
Die TVM führt EVM-Bytecode in isolierten Sandboxes aus, sodass sich die meisten EVM-Verträge mit minimalen Änderungen zu ALUX migrieren lassen. Außerdem bietet ALUX über eine Auswahl häufig verwendeter eth_* JSON-RPC-Methoden eine Ethereum-kompatible Sicht.
