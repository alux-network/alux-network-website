ALUX Network

構建全域虛擬機

設想一個無處不在的邏輯虛擬機——它可以執行在公有區塊鏈、私有叢集，以及手機、瀏覽器等客戶端環境中，而底層的狀態、執行緒、複製與共識都封裝在統一抽象之下。開發者只需編寫一套併發程式；在哪裡執行，只是設定選擇，而不再受限於特定架構。各部分仍會共同提交，形成一個原子結果。這就是虛擬機抽象，也是 ALUX 正在構建的系統。

AI Agent、預約、審批和工作流程可以成為持續服務，而不只是一次性交易。

原生支援 OCAP

  • 命名空間
  • 委託
  • 權限收窄

權限有清晰邊界

OCAP 將權限表示為不可偽造的通道引用。處理程序只能使用自己建立或被顯式傳入的引用；能力還可繼續衰減，並受通道使用方式與生命週期規則約束。

每個任務只獲得完成它所需的能力；與任務無關的權限不會進入目前執行環境。

一筆交易跨越多個分片——路線圖

目標模型把每個參與分片上的更新都暫存於同一交易邊界內。若任一分片內呼叫失敗，所有暫存更新都會在可被觀察前丟棄。目前執行階段尚未實作跨分片執行。

在不要求應用透過 Saga 補償來修復部分提交狀態的前提下，實作橫向擴充。

一個邏輯執行層

TVM 執行、原生 OCAP 支援、跨區塊提交邏輯與 BlockGit 最終性，在一個執行階段抽象中匯合。

這套架構讓鏈上、私有雲端與未來的客戶端設備執行載體共享同一套開發者模型。

ALUX 能實作哪些普通智慧合約做不到的事？
ALUX 將智慧合約模型擴充為面向長時間任務的去中心化持久執行引擎。工作流程可以執行併發處理程序、跨區塊掛起、等待外部工具或人工回應、恢復執行並匯合結果，同時不暴露半完成狀態。由執行階段介導的外部通道可與受支援的鏈下服務互動，無需單獨編排預言機與中繼器。該架構旨在把同一種原子模型橫向擴充，使跨分片影響一同提交或一同中止；跨分片執行仍在路線圖中。
為什麼 ALUX 天然適合 AI Agent？
鏈上AI Agent天然是一筆長交易。呼叫 LLM 或工具需要時間，等待人工回應同樣需要時間；這類工作流程無法被壓縮成瞬時完成的單區塊呼叫。ALUX 使其能夠保留執行上下文、掛起，並在輸入到達後恢復，協調併發AI Agent，再透過可重播執行完成最終確定。
ALUX 只是又一條更快的 L1 嗎？
不是。更快的 L1 加速的是同一種抽象：發生在單個區塊內的一次性狀態更新。ALUX 是面向長交易（Long Transaction）的去中心化併發執行階段；交易可以等待、恢復、匯合多個通道，或選擇第一個就緒的通道，其狀態更新不再受區塊邊界限制。透過 GLVM 架構——虛擬機抽象——同一筆邏輯交易被設計為能夠越過區塊邊界，並進一步延伸到分片與系統邊界。
其他一些區塊鏈也聲稱支援跨區塊交易，ALUX 有何不同？
關鍵詞是原子性。

補償 / Saga： commit → commit → ✗ fail → run compensating undo
每一步都在本地提交，中間狀態可見，補償本身也可能失敗，而且外部影響並非總能撤銷。這屬於最終一致性。包括 ICP 與 Rialo 在內的一些非同步區塊鏈採用了這一模型。它更容易實作，卻不適合需要更強 ACID 保證的應用。

ALUX 全有或全無： stage → stage → ✗ fail → discard everything
只有整筆交易提交時，任何內容才會提交。發生中止時，未提交的影響會被全部丟棄，不會暴露任何局部狀態。這才是跨區塊高度的真正 ACID 原子性。
ALUX 如何保證長交易的確定性？
ReplayTrie 記錄會影響執行結果的非確定性 COMM 選擇，使驗證者能夠在 ALUX 執行階段邊界內逐位元精確地重播同一執行結果。
什麼是物件能力（OCAP）？
物件能力（OCAP）是一種安全模型：一段程式碼只有在被明確授予某項資源的引用（即能力）後，才能存取該資源。在 OCAP 系統中，同一個物件引用既標識資源（designation），也授予使用該資源的權限（authorization）。
為什麼 OCAP 是一種更強且可組合的安全模型？
物件能力（OCAP）之所以是一種更強的安全模型，是因為權限由顯式且不可偽造的能力來表示，而不是依賴全域身份或存取控制清單。它遵循“指稱即授權”（designation is authorization）原則：持有某項能力既標識相應資源，也授予使用該資源的權限，從而消除環境權限（ambient authority）並縮小攻擊面。由於能力可以被安全地委託、衰減和撤銷，安全策略會局部化到相關物件，而不是散落在中心化權限系統中。這使 OCAP 天然具備可組合性：複雜應用、智慧合約和 AI Agent 工作流程可以由各自安全的元件構建，同時仍然遵循最小權限原則。
ALUX 原生支援 OCAP 意味著什麼？
ALUX 的元組空間虛擬機（TVM）在位元碼層直接實作物件能力（OCAP）模型。其指令集不包含任何可偽造或任意構造物件引用的操作，因此能力只能透過顯式委託獲得。這保證了所有權限既不可偽造，也只能被明確轉移。
現有智慧合約開發者能直接用嗎？
TVM 在隔離沙箱中執行 EVM 位元碼，因此大多數 EVM 合約只需少量修改即可遷移到 ALUX。ALUX 還透過一組常用的 eth_* JSON-RPC 方法提供兼容以太坊的視圖。
